# EpiNu — Annotation Review (Claim 2 Human Ghost Audit)

A small static web app that lets Reviewer 1 and Reviewer 2 work through their
assigned images in the browser, records how long each image takes, and exports a
CSV in the same format as the existing `review.csv`.

The point of this app is **not** to change the study. It is a data-entry surface:
fewer transcription mistakes, and a review time that is measured rather than
estimated by hand.

## What this is

- A **static site** — plain HTML, CSS and vanilla JavaScript.
- **No backend, no database, no API, no login.** Nothing is uploaded anywhere.
- Answers live in the browser's `localStorage` until the reviewer downloads the CSV.
- All paths are relative, so it works from any subdirectory on GitHub Pages.

## Source of the reviewer package

The images and task lists are **copies** of the reviewer package generated by the
main research repository:

```
<research-repo>/data/human_ghost_audit/reviewers/
├── reviewer1/{images/, review.csv}
├── reviewer2/{images/, review.csv}
├── assignment_manifest.csv     <- researcher-only, deliberately NOT copied here
└── review_instructions.md
```

- The source repository is **not modified** by this project.
- Images are byte-for-byte copies (verified by MD5), not regenerated. No model
  inference and no image rendering happens here.
- Task order is taken verbatim from each `review.csv`. The app never shuffles,
  re-samples or re-assigns anything.
- `assignment_manifest.csv` is **not** copied into this repository. Nothing
  served by this site records the original file name or which experimental
  condition an image belongs to.

## Stages

The site opens on a stage picker.

- **Stage 1 — Model Error Review** — the original Human Ghost Audit: Reviewer 1,
  Reviewer 2, Reviewer 3 and Final Adjudication. Unchanged.
- **Stage 2 — Ghost-Informed Annotation Review** — Reviewer 1 and Reviewer 2,
  described below.

The two stages share no data, no task lists and no localStorage keys.

## Stage 1 — the three reviewers

| | images | what they see |
|---|---|---|
| Reviewer 1 | 53 | primary review; mixed GT-only and model-output images |
| Reviewer 2 | 53 | primary review; mixed GT-only and model-output images |
| Reviewer 3 | 47 | independent verification; **GT-only images, always** |
| Final Adjudication | 26 | not blind; sees the earlier decisions and, where one exists, the model-assisted view |

Reviewer 3 re-checks a fixed selection of the primary tasks: everything judged
YES or AMBIGUOUS, plus a deterministic 20% QA sample of the NO tasks (seed
`20260813`). Some source images appear in both a Random and a Ghost primary
task, so the 61 selected primary observations collapse to **47 unique images** —
Reviewer 3 reviews each source image exactly once.

Reviewer 3 is shown the original image with the current GT boxes and labels and
nothing else: no model predictions, no FP/FN/TP markers, no experimental
condition, no Reviewer 1/2 judgement, and no original file name. Their
instructions are a separate section in the app and never mention the two kinds of
image that Reviewer 1/2 see.

### Rebuilding the Reviewer 3 images

```bash
python3 tools/build_reviewer3_package.py [--force]
```

Renders the 47 GT-only images from the audit originals and the current COCO
annotations. It uses the fixed selection as-is and never re-selects or re-samples;
if the selection file is missing it stops rather than regenerating one.

### Researcher-only mapping

`data/reviewer3_verification_selection_researcher.csv` maps each `r3_task_id`
back to its `original_file_name` and `linked_primary_task_ids` (plus the linked
reviewers, conditions and primary outcomes). It is **git-ignored**, so it is
never published to the Pages site, and the app never loads it.

Use it after Reviewer 3 finishes to map each R3 judgement back to all of its
linked primary tasks — a single R3 answer applies to both the Random and the
Ghost task when they share a source image.

> Because the file lives under `data/`, a local `python3 -m http.server` in this
> folder would serve it. That is fine for solo use, but do not point a reviewer
> at a local server without moving the file out first.

## Final Adjudication

The last pass. It covers the **26 images where the earlier reviews disagreed**
(21 YES-vs-NO disagreements, 5 defect-type mismatches) and settles what the
annotation should actually say. It is deliberately *not* a blind review and not a
majority vote: the earlier decisions are shown, and where a Ghost Audit
visualisation already exists you can switch to it.

Each screen shows:

- the image with the current GT boxes (the default view),
- **Show model-assisted view** — only on the 24 images that have an existing
  visualisation; the other 2 get no toggle at all,
- the issue and a one-line explanation of it,
- every previous decision: `Primary Review` (or `Primary Review A` / `B` when the
  image was reviewed under both conditions) and `Reviewer 3`, each with decision,
  defect types, classes, count and notes,
- the final decision form.

Unlike the reviewer flows there is **Previous** as well as **Next**, and any
answer can be revisited and changed. `AMBIGUOUS` requires a note — the aim is to
land on YES or NO. There is no timer; review time is not an outcome here.

Progress is saved under `epinu-hga-adjudication-v1`, separate from every reviewer
key.

### Building the queue

```bash
python3 tools/build_final_adjudication.py [--force]   # needs openpyxl + Pillow
```

Reads the `Adjudication Queue` and `Task Details` sheets of the Confirmation
workbook, renders the 26 GT-only images from the audit originals, and copies the
existing ghost visualisations for the model-assisted views. **No inference runs
and no visualisation is regenerated.** The workbook is opened read-only and never
written back.

`QA Misses` (primary said NO, Reviewer 3 said YES) is a separate list and is not
part of this queue. One source image legitimately appears in both, via two
different primary tasks — the queue holds its ghost task, QA Misses holds its
random task.

### Output

`claim2_final_adjudication_completed.csv`, in queue order:

```
queue_id,final_defect_found,final_defect_types,final_target_classes,final_number_of_defects,final_adjudication_notes
```

Merge it back into the workbook on `queue_id`. The site never publishes the
original file names, so `original_file_name` is not in the exported CSV — join it
from `data/final_adjudication_mapping_researcher.csv` (git-ignored,
`queue_id,image_id,original_file_name`) if you need it.

## Stage 2 — Annotation Review

Tests whether the class-level problems found in Stage 1 help when reviewing
*different* images. The population is `<research-repo>/data/claim2/ghost_audit/train`
(2,902 images); the 728 Stage 1 pseudo-test images are a disjoint split and are
not used.

180 images across three classes, each with the focus problem Stage 1 flagged:

| class | focus problem | GENERAL | GHOST_INFORMED |
|---|---|---|---|
| Tomato_Raw | MISSING_LABEL | 30 | 30 |
| Lemon | MISSING_LABEL | 30 | 30 |
| RedOnion_Raw | BBOX_ERROR | 30 | 30 |

**Both conditions see identical GT-only images, the same form, the same timer and
the same zoom.** No model output appears anywhere in Stage 2. The only difference
is whether the class-specific focus note is shown.

### Reviewer design

Two reviewers, identified only as **Reviewer A** and **Reviewer B**. Each takes
exactly **one condition per class** — 90 tasks each:

| class | GENERAL | GHOST_INFORMED |
|---|---|---|
| Tomato_Raw | Reviewer A | Reviewer B |
| Lemon | Reviewer B | Reviewer A |
| RedOnion_Raw | Reviewer A | Reviewer B |

Tomato_Raw and Lemon are fixed by design. RedOnion_Raw was drawn from seed
`20260819` and then **frozen** in `data/stage2_class_roles_researcher.json`
(git-ignored); later runs read the frozen map rather than redrawing, and the draw
is deterministic so a fresh checkout reproduces it.

Nobody reviews the same class both informed and uninformed: once a reviewer has
seen the hint for a class they cannot go back to being uninformed about it. The
roles alternate across classes so each reviewer carries both, and reviewer
effects do not all push in one direction.

> **Known limitation.** With only two reviewers, reviewer and condition are
> confounded *within* a class — for Tomato_Raw, "Reviewer A" and "GENERAL" are
> the same set of observations, so a class-level difference cannot be attributed
> to the condition alone. Alternating the roles across the three classes keeps
> the confound from running one way overall, but it does not remove it. This is
> a constraint of the available reviewer pool and should be stated in any
> analysis. It is deliberately not shown in the reviewer-facing UI.

### Blinding

The reviewer-facing payload contains no condition label. `tasks.json` holds only
`task_id`, `image`, `class_name`, and `focus_information` on the informed tasks —
so a reviewer cannot read off that they are the control arm for a class. The UI
shows only "Stage 2 — Annotation Review" and never the words GENERAL or
GHOST_INFORMED.

### Building the packages

```bash
python3 tools/build_stage2_packages.py [--force]   # needs Pillow
```

Reads the fixed review set (`<research-repo>/data/claim2/stage2/stage2_review_manifest.csv`).
The GENERAL / GHOST_INFORMED assignment and the 180-image selection come from
that manifest and are never recomputed.

### Output

`claim2_stage2_reviewer_a_completed.csv` / `..._reviewer_b_completed.csv`:

```
task_id,reviewer_id,class_name,condition,defect_found,defect_types,target_classes_affected,number_of_defects,notes,review_time_seconds
```

`reviewer_id` is `reviewer_a` / `reviewer_b`. `condition` is retained for the
analysis but never displayed. `number_of_defects` is the total number of defects
found in that image. Original file names are not published; join them from
`data/stage2_assignment_researcher.csv` (git-ignored) on `task_id`.

## Privacy

No personal name appears anywhere in this repository — not in HTML, JavaScript,
JSON, CSV, localStorage keys, comments, tests or this README. Reviewers are
`reviewer1`/`reviewer2`/`reviewer3` in Stage 1 and `reviewer_a`/`reviewer_b` in
Stage 2. The mapping to real people is kept offline by the researcher; there is
deliberately no mapping file in this repository.

Paths to the research repository are configured with `EPINU_RESEARCH_ROOT`
(defaulting to a sibling checkout) rather than hard-coded home directories.

`tests/verify_package.py` checks this. It takes the names to search for from the
environment so that no personal name is written into the test itself:

```bash
EPINU_NAME_TOKENS="name1,name2" python3 tests/verify_package.py
```

It also always checks, with no configuration, that no tracked file embeds an
absolute home-directory path.

The app fetches `tasks.json`, so it needs to be served over HTTP — opening

```bash
# then open http://localhost:8000/
```

## How a review runs

1. The reviewer picks Reviewer 1, 2 or 3 (no password).
2. A brief screen shows the task count, the six target classes and the rules.
3. **Start Review** shows the first image and starts the timer.
4. For each image: `NO`, `YES` or `AMBIGUOUS`. `YES` requires at least one
   defect type, at least one affected target class, and a count of 1 or more.
5. **Next** saves the answer with its elapsed time and moves on. There is no way
   back — this is deliberate, so later images cannot change earlier answers.
6. After the last image (53, or 47 for Reviewer 3) the completion screen offers
   **Download CSV**.

Timing details:

- The clock runs only while the reviewer is actually on the review screen.
- **Pause** stops it; paused time is excluded.
- Switching tabs or backgrounding the window pauses it automatically. It never
  restarts on its own — the reviewer has to press **Resume**.
- Opening the instructions from the review screen also pauses it.

Progress is written to `localStorage` after every image, under a separate key per
reviewer (`epinu-hga-review-v1:reviewer1` / `...:reviewer2`), so a reload or a
closed browser resumes where it left off. Downloading the CSV does not clear it —
the file can be downloaded again.

## CSV output

Filename: `reviewer1_review_completed.csv`, `reviewer2_review_completed.csv` or
`reviewer3_review_completed.csv`.
Rows are in task order. UTF-8 with a BOM (so Excel opens it correctly), CRLF line
endings, RFC 4180 quoting.

Columns — identical to the existing `review.csv`:

| column | values |
|---|---|
| `task_id` | `HGA_XXXX` (Reviewer 1/2) or `R3_XXXX` (Reviewer 3) |
| `reviewer_id` | `reviewer1` / `reviewer2` / `reviewer3` |
| `defect_found` | `YES` / `NO` / `AMBIGUOUS` |
| `defect_types` | `;`-separated: `MISSING_LABEL`, `WRONG_CLASS`, `BBOX_ERROR`, `GRANULARITY_MISMATCH`, `SPURIOUS_LABEL`, `OTHER`, `NONE` |
| `target_classes_affected` | `;`-separated target class names |
| `number_of_defects` | integer |
| `notes` | free text |
| `review_time_seconds` | integer, measured automatically |

Conventions: `NO` is stored as `defect_types=NONE`, `number_of_defects=0`, with
no affected classes. `AMBIGUOUS` leaves the detail fields empty — the judgement
is in `defect_found`, with any explanation in `notes`.

Example:

```csv
task_id,reviewer_id,defect_found,defect_types,target_classes_affected,number_of_defects,notes,review_time_seconds
HGA_0001,reviewer1,NO,NONE,,0,,23
HGA_0002,reviewer1,YES,MISSING_LABEL;BBOX_ERROR,Tomato_Raw,2,"two tomatoes at the back, unlabelled",71
HGA_0003,reviewer1,AMBIGUOUS,,,,too blurry to call,44
```

## Live site

**https://digital-health-disparities-initiative.github.io/epinu-ghost-audit-review/**

This is the URL to give the reviewers. No login, no setup — they open it, pick
their reviewer ID and start.

Published from the `main` branch (root) of
`digital-health-disparities-initiative/epinu-ghost-audit-review`. Pushing to
`main` redeploys automatically; there is no build step, and `.nojekyll` makes
GitHub serve every file as-is.

**The site and repository are public.** Anyone with the URL can view all 106
review images. The page sends `noindex, nofollow`, which discourages but does not
guarantee exclusion from search engines. To take it down: **Settings → Pages →
Unpublish site**, or make the repository private.

### Deploying changes

```bash
git add -A && git commit -m "..." && git push
```

Pushing needed three local settings, already applied to this clone:

```bash
# 19 MB of images in a single push
git config --local http.postBuffer 524288000

# Take the token from the gh CLI instead of a stale keychain entry
git config --local credential.helper ""
git config --local --add credential.helper \
  '!f() { echo username=x-access-token; echo "password=$(gh auth token)"; }; f'

# The remote is set to https://x-access-token@github.com/... on purpose (below)
```

**Why the odd remote URL:** the machine's *global* git config contains

```
url.https://<user>:<personal-access-token>@github.com/.insteadOf  https://github.com/
```

which rewrites every plain `https://github.com/...` URL to embed a hardcoded
username and an expired token, bypassing all credential helpers. Qualifying the
remote as `https://x-access-token@github.com/...` no longer matches that prefix,
so the rewrite does not fire and the helper above is used instead. If that global
rule is ever removed, the remote can be simplified back to the plain URL.

## Reviewer instructions

The in-app **Review instructions** screen is the reviewer-facing copy, adapted
from `review_instructions.md` in the source package. It covers the six target
classes, the six defect types, and how to treat the two kinds of image —
including that model output is a hint, is not necessarily correct, that a
model/annotation disagreement is not by itself an annotation error, and that the
whole image must be checked rather than only the places the model pointed at.
